# 换名称 / 换 logo：改源码还是做插件

> 结论：**品牌不在插件的能力范围内。** 插件能改行为（登录、账户、界面细节），
> 但应用菜单、关于弹窗、图标、安装包这些"产品身份"只存在于 Electron 主进程和
> 打包配置里，插件碰不到。

---

## 1. 什么能改，什么不能

| 需求 | 做法 | 原因 |
|---|---|---|
| 侧栏品牌名、主题色、隐藏个别入口 | 插件（CSS / slot） | Web 渲染层，插件有注入点 |
| 加载页首屏文案 | 插件 + `webserver/index-inject` | 硬编码且渲染早于插件加载，只能从 Host 注入首屏样式 |
| 应用菜单、关于弹窗、窗口标题、托盘、exe 图标、安装器、appId、更新源 | **改源码 / 重新打包** | 主进程与打包层，插件无 API 可接 |
| 登录方式、账户数据、业务行为 | 插件 | Host 服务层，插件正是为这层设计的 |

判断口径：**插件改行为，品牌是产品身份；身份落在源码和打包配置里。**

---

## 2. 为什么：品牌的三个可见层

| 层 | 典型可见项 | 插件可控性 |
|---|---|---|
| Web 渲染层 | 侧栏品牌、预览版标记、文案、配色 | 能 |
| Host 服务层 | 账户资料、加载页首屏 HTML、自定义页面路由 | 部分能 |
| Electron 外壳 + 打包 | 应用菜单、关于弹窗、窗口标题、托盘、图标、安装器、appId、自动更新 | **完全不能** |

只改前两层，就会得到"侧栏叫大伟的智能体、关于里还是 DeepSeek Harness"这种半截品牌。

---

## 3. 三个实测案例

**① 侧栏品牌名（能改）**
`dsh-skin-techno-neon` 用样式替换 `brandMark` 的文字：

```css
[class*="brandMark"]::after { content: "大伟的智能体"; }
```

依赖 DSH 的 CSS Modules 保留 local 名才能命中；折叠态的 `railMark` 要单独处理。
**没有编译期保护**，上游改结构就静默失效。

**② 加载页（半能改）**
加载页文案在 `packages/client/web/src/boot-page.ts` 里硬编码，渲染发生在插件加载之前。
插件只能从 Host 监听 `webserver/index-inject`，往首屏 HTML 塞一条样式表顶替文案
（`lib/index.js` 的 `BOOT_BRAND_CSS`）。能成，但已经是"绕道服务端改渲染层"。

**③ 应用菜单 + 关于弹窗（改不了）**

| 项 | 位置 |
|---|---|
| 菜单项 | `apps/desktop/src/main.ts` 的 `applicationItems()` |
| 弹窗内容 | 同文件 `showAbout()`：`title = aboutMenu`、`message = aboutProduct`、`detail = aboutVersion` |
| 文案字典 | `apps/desktop/src/locale.ts`（`zh` / `en`） |
| 版本号 | `app.getVersion()`，即 `app.asar/package.json` 的 `version` |
| 成品 | `<dsh-install-dir>\resources\app.asar` 的 `lib/main.js` |

弹窗是主进程自己的 `BrowserWindow` + 独立 preload（页面 `dsh-app://shell/update-dialog.html`），
插件既没有 API 也没有注入点。

## 4. 两条路的成本

| | 插件 | 改源码（薄 fork） |
|---|---|---|
| 生效速度 | 装完即生效，可随时卸载 | 要重新打包 + 签名 |
| 覆盖面 | 只有 Web / 部分 Host | 全部，含原生外壳与安装包 |
| 失败方式 | **静默失效**（选择器没命中、文案 key 变了） | 编译期报错，容易发现 |
| 维护成本 | 依赖内部实现（CSS Modules 名、DOM 层级），要 `MutationObserver` 兜底 | 跟上上游合并，冲突面可控 |
| 适用 | 单一部署的界面微调 | 对外交付 / 长期维护 / 多品牌 |

---

## 5. 决策规则

按顺序问四个问题，任一为"是" → 改源码：

1. 涉及**原生菜单 / 对话框 / 窗口标题 / 托盘 / 安装器 / 图标 / appId**？
2. 这个品牌要**对外交付或长期维护**？
3. 需要**多套品牌并行**（不同客户、不同产品名）？
4. 上游升级时，**不能接受某个界面悄悄变回官方**？

都为"否"→ 插件更划算：轻、可逆、不碰安装包。

## 6. 落地清单（改源码时）

| 目标 | 文件 |
|---|---|
| 菜单 / 关于 / 托盘 / 退出文案 | `apps/desktop/src/locale.ts`（`zh`、`en` 都要改） |
| 应用名、安装包名、协议名 | `apps/desktop/scripts/electron-builder-config.mjs`（`productName` / `artifactName` / `protocols`） |
| exe / 关于 / 托盘图标 | `apps/desktop/resources/*`（`icon-windows.png`、`icon.png`、`tray.ico`） |
| 欢迎页品牌图 | `apps/desktop/renderer/assets/welcome-brand.svg` |
| 加载页文案 | `packages/client/web/src/boot-page.ts`（直接改，可去掉上面的注入绕路） |

**两个不能随手动的字段：**

- `app.name` / `appId`：Electron 用它推导 userData 目录，改了等于换配置目录，
  `~/.dsh` 下的凭证、profile、已装插件都会"消失"；`appId` 还绑着更新通道和签名。
- `version`：`app.getVersion()` 同时被"关于"弹窗和 electron-updater 用于版本比较。
  只想改显示，就改 `aboutVersion` 文案，不动版本号。

**应急手段**：直接改安装目录 `app.asar` 里 `lib/main.js` 的字面量，立即生效；
但更新 / 重装会被覆盖，且 asar 头里每个文件带 SHA256 integrity，替换时要同步更新。
只适合临时演示。

**更优解**：推动上游把 `productName`、文案字典、logo 路径做成 config 字段，
升级天然无痛，也不用维护 fork。

---

## 7. 一句话总结

> 插件是行为层的扩展点，不是品牌层的皮肤工具。
> 界面小改动用插件；涉及原生外壳、打包产物和交付形态，就回源码改——
> 那里改得干净，也坏得响亮。
